# 更新を共有する・取り込む

コードは AGPL-3.0、`docs/` と書き出した絵は CC BY 4.0（[decisions.md](decisions.md) の「ライセンス（078）」）。ほかの会社・ほかの業界の人が、プロンプトや絵の部品を直して返してくれれば、同じ仕組みを使う全員の精度が上がる。

ただし、よかれと思った直しで精度が落ちることがある。取り出しのプロンプトを 1 行変えるだけで、漏れや危ない読み違いが増えうる。だから、取り込むたびに評価をやり直し、前の点より下がっていたら止める。

## 共有のしかた

- GitHub の PR で送る。会社のデータ・マニュアルの本文・人の名前は入れない（リポジトリにはもともと入れていない）
- 取り出しのプロンプトや採点を変えたときは、鍵を持っていれば手元で `npm run intake -- --base origin/main --run-paid` を流し、`docs/numbers.md` に増えた行も PR に入れる。鍵が無ければ入れなくてよい（受け取る側が流す）

## 精度に効く場所（`scripts/intake-check.ts` の AREAS）

| 場所 | 中身 | 取り込むと走るもの |
|---|---|---|
| `src/shared/extract/` | 取り出しのプロンプトと決まり | 型・単体テスト・調整用の 20 個の評価（API） |
| `src/shared/eval/` | 採点の判定と数え方 | 同上 |
| `eval/items_tune_*` | 評価データ（調整用の 20 個） | 前の点と比べられないので止める。人が中身を確かめて基準を作り直す |
| `src/shared/verify/` | 危ない読み違いの安全網 | 型・単体テスト |
| `src/shared/make/`・`eval/prompts/`・`src/shared/card.ts` | 脚本と絵の下書きのプロンプト | 型・単体テスト。見た目は監修者が見直す |
| `src/shared/picto/` | 絵の部品（ピクトグラム） | 同上 |

絵の部品・絵のプロンプト・確かめる AI（`src/shared/verify/`）の変更は、20 個の評価では測れないので、人が見直して `--reviewed` を付けるまで「評価が要る」（終わりのコード 2）で止める。

最後の確認用の 10 個（holdout）は、取り込みでも読まない。

## 取り込むと何が走るか

- 手元: `npm install` のときに `.git/hooks/post-merge` へ見張りが自動で入る（git は clone でフックを写さないので、package.json の prepare で入れる。入れ直すときは `npm run intake:install`。前からある pre-commit などには触らない）。`git merge`・`git pull` のあと、精度に効くファイルが変わっていれば、型と単体テストを流し、20 個の評価が要るかを調べる
  - 手元の作者のコミットだけ（もう 1 台の PC からの pull）で、同じ中身の評価がもう記録にあれば、その結果を使う。ほかの人のコミットが入っていれば流し直す
  - 20 個の評価は Claude の API を呼ぶので、勝手には流さない。見込みの費用（近い 5 回の最高の 1.2 倍）と今日の合計・1 日の上限を出し、`--run-paid` を付けたときだけ流す。上限を超えるなら流さない
- CI: PR のたびに `.github/workflows/intake.yml` が同じ見分けをする。鍵を渡さないので API は呼ばない。PR に新しい評価の行が入っていれば前の点と比べ、無ければ「評価が要る」で止める。型と単体テストは `test.yml` が流す

## 落ちたらどうなるか

- 比べ方: 危ない読み違いが 1 件でも増えたら落ちる。組（合った数）・漏れ・取り出しすぎは、判定に AI を使う揺れの分として 2 件まで許す（`INTAKE_TOLERANCE` で変えられる）
- 終わりの番号: 0 通った・1 落ちた・2 評価が要る・3 基準が変わった
- 手元で落ちたとき: merge はもう済んでいるので、`git reset --merge ORIG_HEAD` で戻す。戻し方は画面に出る
- 結果は `eval/intake-log.md` に 1 行ずつ足す（追記だけ）。何を取り込み、前と後の点がどうだったかが残る
