# 作業の表

軸（[compass.md](compass.md)）をコンパスにして、やることを 30〜40 分のマスに分けた表。日程の区切り（製品仕様 §9）を**目印**にし、その間をマスで埋める。どの目印にもつながらない作業は入れていない。2 つの案を別々に作り、突き合わせて 1 本にし、作る側の目で見直して重いマスを割った（違いと採った理由は [decisions.md](decisions.md)）。

## 読み方

- 現場の確認の日は 11/6 を本線にする（11/5 になったときは末尾）
- **前**: そのマスを始める前に終わっていないといけないマス。表の中で自分より上のマスだけを指す。ID の a・b は、見直しで 2 つに割ったマス。後ろの順番は、そのマスを「前」に持つマス
- **確かめ方**: 「自動テスト」（フックで流れるテスト）か「録画」（Playwright か画面の録画・撮影）。ファイルがあるだけでは済ませない
- **★**: 一番遅れてはいけない筋。現場の確認の日の前夜までに終えるマス（当日のマスには付けない）。夜間の仕分けの一覧と約 120 枚の下書きを含む。★ のマスの「前」は全部 ★
- **見込み**: 分。1 マス 30〜40
- **筋**: 進路図（進み具合の画面）でどの筋に並べるか。ピクト（文字 → ピクトグラム）・安全網・直し（直しと人の確認）・折りたたみ（情報量を保つ）・土台（土台と見せ方）のどれか 1 つ。振り分けの考え方は decisions.md
- **状態**: 済み・途中・まだ。**実際の分**: かかった分。マスを始めた時刻から終えた時刻までの実時間（切り上げ）で、`python tools/progress.py --done <ID> --start <始めた時刻>` が数えて書く。11/2 は「1 つ前のコミットからそのマスのコミットまで」で数えたが、3 本のスレッドが並んで動いた間はそれが作業の時間にならないので、決まりと合わない 20 行は数え直さずに「（目安）」の印を付けた（進み具合の合計にも「目安を含む」と出る）。**コミット**: そのマスを終えたコミット。マスを終えたら、状態と実際の分を書いてからコミットする。自分のコミットの番号はまだ無いので「直近」と書き、次のマスのコミットで番号に書き換える。書き換える番号は、件名の頭にそのマスの番号があるコミット（`tools/progress.py --done` がそう書き換える。HEAD を写すと、間に挟まった別のコミットの番号が入る）。続きのコミットがあるマスは、古い順に「, 」で並べる
- **マスの外の仕事**: 件名に番号の無いコミットで、どのマスにも当たらない仕事は、あとから新しいマスにする（番号は今の続き、状態は済み、★ は付けない）。既にあるマスの一部なら、そのマスのコミット欄に足すだけ。115〜119 は 11/2 の夜〜11/3 の 0 時台に、120・121 は 11/3 に足した
- **後から生まれたマス**: 作業の欄に「後から足した」とあるマス。最初の表に無く、直しや新しい観点から足したもの。進路図では筋の上に並べず、右下の枠に筋の色の箱でまとめる
- **※取り直し**: 確かめ方の欄にこの印があるマスは、録画に絵（ピクトグラム）が映る。絵がまだ決まっていないので、いまの録画は「直す前」の素材として残し、絵が決まったら撮り直す（11/3 作者）。これから録画に絵が映るマスを足すときも、確かめ方にこの印を付ける。一覧は progress.md の末尾
- 進み具合は `python tools/progress.py` がこの表と軸から [progress.md](progress.md) と [dashboard.html](dashboard.html) に作る（手で書かない）。コミットの前のフックが、表と progress.md のずれを止める
- マスを済みにするときは、同じコミットで [flow.md](flow.md) のその行も直す（「まだ・」を外す）。外さないと flow.md のテストが落ち、直す行を示す
- 008 は作者の依頼で、仮の流れ（`scratch/`）を使って、007 より前に済ませた

## 1b. 絵の合格の線（ピクトグラムの見た目）

正式な絵は、安全標識や非常口のマークのような**ピクトグラム**にする。文字が無くても一目で意味が分かる絵柄（11/2 作者）。

- 人: 線の棒ではなく、頭・胴・手足が塗りの形でつながったピクトグラムの人
- 役: かぶり物の形で一目で分かる（新人＝白いヘルメット、上の人＝黒い帽子）
- 道具: 盤や検電器は角の丸い箱と丸で、何の道具か分かる
- 地面の線がある
- 吹き出しの中に「？」や「✓」を描き、迷っている・確かめた、を絵で出せる
- 1 つの決まりを 3〜4 コマのピクトグラムの紙芝居で見せる
- 例外（11/7 既定・作者の確認待ち）: 原則のカード（本文の `shape` が principle）だけは 1 コマ（印の付いたキーフレーム 1 つ）を許す。作る画面で「原則の 1 コマで作る」を選んだときだけ作る。ほかのカード（shape が無い・story）は 3〜4 コマのまま
- 同じ日に足した型（どれも既存の署名済みのカードに項目を書き足さない。無い項目は今までどおりに読む）:
  - 束（`bundle`）: 1 つの取り出しの同じ親の決まりから作った枚を、束の名前・何枚目・全部で何枚・親の決まりの文でまとめる。一覧と読む口では、束の最初の 1 枚の場所に順に並べる。1 つの束は 30 枚まで
  - 重さ（`weight`）: 監修者が「命に関わる」か「ふつう」を決める（無い＝ふつう）。命に関わるカードの赤い縁は絵の中に置かず、読む画面の絵の外側と、書き出し・印刷の外枠にだけ置く
  - 掲示の版: 1 枚のカードのコマを大きく 1 枚にまとめた横長の貼り紙（文の列とふりがな・版と日付・命に関わるなら赤い縁）と、原則のカードを 1 列に並べた版
  - 朝礼の組: その日の作業を言葉で書くと、合いそうな署名済みのカードを最大 8 枚出す（命に関わるカードを先に）。選んだ組を残す（追記だけ）
- 作り方（079b で比べて決めた）: Opus 5.5 が、1 つの決まりを「動き」として、部品（人の関節・小物・吹き出し）のキーフレームの並びを JSON で書く。描く側がそれを動かし、意味の変わる 3〜4 か所をコマとして PNG に切り出す。部品と JSON の形は残す（監修者が部品を直せるように、確かめる AI の記録が残るように）。同じ動きを、画面の紙芝居の演出と動画にも使う
